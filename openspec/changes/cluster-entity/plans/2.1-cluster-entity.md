# 2.1 One cluster table in `entities/cluster`

## Why

What an endpoint of ours is (its key, the cluster it talks to, its name, public URL, the platform RPC the env sets,
the read-buffer RPC and the send cap) is spread across five modules, and three of them rebuild the key-to-URL
mapping on their own:

| Module | Its copy |
| --- | --- |
| `src/constants/connection.ts` | `Endpoint`, `CLUSTER_NAMES`, `Network`, `buildNetworks`, `NETWORKS`, `DEFAULT_ENDPOINT` |
| `src/shared/config/client-env.ts` | the raw env groups, keyed `mainnet` |
| `src/utils/connection.ts` | `getKnownCluster`, and the read-buffer and send-cap lookups re-keyed to `mainnet-beta` |
| `src/settings/stored-endpoint.ts` | `buildEndpointOptions`, whose entry order decides which URL a key reads back as |
| `src/entities/custom-rpc/model/custom-rpcs.ts` | `CHIPS`, `ADOPTED_CHIPS`, the Testnet name map |

Adding Testnet's env touched all five, and missing one saved the platform Testnet URL, API key included, into
`localStorage`. The rule "`localStorage` holds a chip's key, and a URL only for a custom RPC" is a convention in
`toStoredEndpoints`, not a type.

## Target

A slice `src/entities/cluster` (public API `index.ts`):

- `model/clusters.ts`: the cluster type (`devnet`, `testnet`, `mainnet-beta`, `localnet`, `playnet`), the key type
  (a cluster, or `surfpool`), and one record per key in Settings' order: Mainnet, Devnet, Testnet, Localnet,
  Surfpool, then Playnet. A record holds its key, the cluster it talks to (Surfpool's is `localnet`), name, public URL,
  the URL it resolves to (the env's platform RPC, else the public one), whether Settings offers it as a chip (all
  but Playnet), the read-buffer RPC and the send cap. The env's `mainnet` key is mapped to `mainnet-beta` here, once.
  `shared/config/client-env.ts` stays the only reader of `process.env`.
- A selection type: `{ key: <key> }` or `{ cluster: "custom"; url: string }`. Only the custom arm carries a URL.
- `model/custom-rpcs.ts` and `model/health.ts`: `PgCustomRpcs` and `fetchRpcHealth`, moved whole from
  `entities/custom-rpc`, which is deleted. They join this slice because entities do not import each other, and the
  saved list is the custom arm of the selection. The chip addresses `PgCustomRpcs` refuses or never adopts derive
  from the table, so Testnet, Localnet and Surfpool are covered by their chips.

The callers read the slice instead of keeping a copy:

- `settings/stored-endpoint.ts`: the connection entries of `buildEndpointOptions` come from the table, and the
  connection endpoint is stored through its selection; the server entries stay.
- `utils/connection.ts`: `getKnownCluster`, `getReadBufferConnection` and the send cap read the table.
- `constants/connection.ts`: `Network`, `NETWORKS`, `DEFAULT_ENDPOINT` and `clusterName` derive from the table. The
  prose helpers (`networkInSentence`, `solOn`, `UNKNOWN_NETWORK`) stay.
- `widgets/settings-page`: imports `PgCustomRpcs` and `fetchRpcHealth` from `@/entities/cluster`.

## Must not change

- What `localStorage` holds: `settings` keeps `{ "option": <key> }` and `{ "option": "custom", "url": … }`, every key
  stored before (the `*-platform` keys, plain strings) still reads back as it does now, and `customRpcs` keeps its key
  and shape.
- Behaviour, ids, `aria-label`s and test ids. Every scenario in `openspec/specs/client-v2-custom-rpcs/spec.md` holds
  as before, and the in-source tests of `stored-endpoint.ts` and `custom-rpcs.ts` keep their assertions.

## Out of scope

- Moving genesis-hash detection out of the slice's `api/`.
