# The Build and Deploy stages (5.11) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Build and Deploy stages are drawn with the design system's `StageEmpty`, `Diagnostic`, `DropZone`, the buttons and the Deploy result block, with one accent action per screen and that action at the foot on a phone; the unreachable legacy `views/sidebar/build-deploy/Component` is deleted.

**Architecture:** By the UI move rule, `Build.tsx` and `Deploy.tsx` import UI of ours (`IdlActions`), so each gets a `Base` beside it: `BaseBuild.tsx` and `BaseDeploy.tsx` render from props only; `Build.tsx` and `Deploy.tsx` stay as the connected wrappers. The choice of Build surface moves out of the component into a pure `buildSurface()` in `build-surface.ts`, returning a discriminated union. Every styled-component in the two stages and `IdlActions` goes; Tailwind on the design-system tokens replaces it.

**Tech Stack:** React 19, Tailwind 4, shadcn on Radix (design-system registry), vitest + Testing Library, Playwright.

**Spec:** `openspec/changes/ui-migration/design.md` section "Build and Deploy stages (5.11)" and `specs/client-v2-stages/spec.md` (both written in Task 1); HOO-2066.

## Global Constraints

- `shared/ui` is installed, never edited by hand: `yarn ds-add <name>`. Layout around a DS part is a `className` on it, not an edit of the part.
- Ids, `aria-label`s and test ids do not change: `flow-stage-panel-*`, `flow-stage-tab-*`. The texts e2e reads stay: "Build", "Building...", "Build succeeded", "Rebuild", "Retry build", "Continue to Deploy", "Deploy to <cluster>", "Deploying...", "Upgrading...", "Redeploy to <cluster>", "Fix with assistant", "Download IDL", "Load IDL file", "Export project".
- Build, Retry build and Rebuild are `AsyncButton` (design.md "Buttons (5.4)"); a stage shows at most one `BrandButton` (`client-v2-buttons: The Build stage offers Deploy as a brand button`).
- Every `AsyncButton` and `CopyButton` passes `onError={reportButtonFailure}`.
- No empty `catch`; failures log through `createLogger("flow:<module>")`. A rejected IDL file is the user's input, not a fault: logged at `warn` without `report: true`.
- No nested ternaries: two or more branches is an `if` chain or a `Record` lookup.
- Tests: no spread to build a new fixture shape (client-v2/AGENTS.md).
- Node 22.20 (`source ~/.nvm/nvm.sh && nvm use`); every command runs from `client-v2/`.
- Commits: Conventional Commits, `(client-v2)` scope; no AI attribution.
- Do not edit files the open element/phone PRs own: `widgets/layout-shell/**`, `components/Tabs/**`, `views/flow/console/**`, `views/flow/header/**`.

## Review Focus

1. A diagnostic whose file is not open or whose line is past the end of the file: the card falls back to rustc's excerpt, never an empty source block (pin in Task 3, `diagnosticView`).
2. A build that fails with stderr the parser cannot split: the screen still says "Build failed" with the stepper's count and offers "Fix with assistant", never "0 errors" (pin in Task 3).
3. A dropped file that is not JSON, or JSON without `instructions`: the drop zone says "Not an Anchor IDL JSON file", the IDL is unchanged, and the warning is logged (pin in Task 5).
4. A second click on Deploy while one runs: nothing starts (pin kept in `Deploy.test.tsx`, Task 6).
5. A phone with a short stage: the action sits at the foot of the stage, not under the text (pin in Task 8's e2e).

```markdown
### Requirement: The Build stage explains a failed build
The Build stage SHALL show each compiler error as a diagnostic with its code,
a plain explanation and the source lines around it, the faulty line marked.

#### Scenario: A failed build marks the faulty line
- **WHEN** a build fails with a type error in `src/lib.rs` line 5
- **THEN** the stage shows a diagnostic naming the error
- **AND** line 5 is marked as the faulty one, with rustc's label beside it
- **AND** "Fix with assistant" is offered

### Requirement: The Deploy stage shows the latest deployment
After a deploy the Deploy stage SHALL show the program id with a copy button,

#### Scenario: A deployment shows its program id to copy
- **WHEN** the project has been deployed
- **THEN** the Deploy stage says where it was deployed
- **AND** shows the program id with a button that copies it

### Requirement: A stage's action sits at the foot on a phone
Below 768 px the action row of the Build and Deploy stages SHALL sit at the
foot of the stage.

#### Scenario: The Build action at the foot on a phone
- **WHEN** the Build stage is shown on a 390 px wide screen with nothing built
- **THEN** the Build button sits at the foot of the stage
```

```ts
export type BuildSurface =
  | { kind: "restored"; failed: boolean }
  | { kind: "unreached" }
  | { kind: "empty" }
  | { kind: "succeeded" }
  | { kind: "failed"; stderr: string };

export const buildSurface = (input: {
  flow: Pick<FlowState, "build" | "buildSettled" | "buildStartedAt">;
  own: BuildOutput | null;
}): BuildSurface;

// build-view.ts
export interface SourceLine { num: number; text: string; failing: boolean }
export interface DiagnosticView {
  code: string | null;
  title: string;          // humanized
  explanation: string;    // humanized + "Rustc says: <label>."
  label: string | null;   // rustc's text after the carets
  file: string | null;
  lines: SourceLine[] | null;  // null -> show `excerpt`
  excerpt: string;
  prompt: string;         // what "Fix with assistant" sends
}
export const extractLabel: (excerpt: string) => string | null;
export const sourceLines: (d: BuildDiagnostic, content: string | null) => SourceLine[] | null;
export const diagnosticView: (d: BuildDiagnostic, content: string | null) => DiagnosticView;
export const msLabel: (ms: number | null) => string | null;
export const errorMeta: (n: number, ms: number | null, host: string) => string;
export const warningCount: (raw: string) => number;
```
