# 6.5 e2e for the flow, desktop (HOO-2364)

Goal: Playwright walks Hello Anchor from the intro card to the finish card on
desktop in CI's e2e job, with no network, so a regression in the
conversation, the runs or their wiring fails the PR that brings it.
The phone half of 6.5 is HOO-2510.

## Approach

The specs drive the real app and the real runners. What CI lacks is the
network, so the test answers it:

- **Build server** (`e2e/fake-build-server.ts`): `POST **/build` fails with
  the real E0412 log (`PLANNED` in `model/build-logs.fixture.ts`) while
  `lib.rs` has no `struct Hello`, and passes otherwise with a stable uuid and
  an Anchor 0.29 IDL derived from `lib.rs` (`hello`, plus `name: string` when
  the signature takes it), and a uuid per program. `GET **/deploy/<uuid>`
  serves a few KB of bytes whose first byte marks which `hello` was built. A
  build with no `lib.rs` or a deploy of an unknown uuid is refused and listed.
- **Devnet** (`e2e/fake-devnet.ts`): a stateful JSON-RPC fake on
  `https://api.devnet.solana.com` plus `routeWebSocket` on its `wss://`. It
  decodes each sent transaction with `@solana/web3.js` in the test process and
  applies what the tutorial sends: the system program's createAccount and
  transfer, compute-budget instructions (ignored), the
  upgradeable loader's initialize buffer, write, deploy, upgrade and extend,
  and a call to `hello`, logged only on a program the loader deployed and
  from the bytes deployed there (`Hello, World!`, or `Hello, <name>!`). A
  transaction applies to a draft of the accounts and lands only if no balance
  goes below zero, no write runs past an account's end and every account an
  instruction names exists; otherwise it answers a JSON-RPC error and changes
  nothing. `simulateTransaction` always passes.
  Slots advance every 400 ms; `signatureSubscribe` is notified once its
  transaction lands, and `accountSubscribe` on every change to its account. `requestAirdrop` credits the wallet, or answers a
  JSON-RPC error when the test refuses it. Any other method, program,
  instruction or subscription fails and is listed in `unhandled`, which every
  spec that runs on the fakes asserts empty.
- **Copy from the definition**: the specs read questions, options and the
  win headlines from `src/tutorials/hello-anchor/tutorial.json`, so tuning the
  content (HOO-2361) does not break them. Only the cards' own UI strings
  ("Build failed", "Not enough devnet SOL", "Upgraded") are literal.

## Specs (`e2e/tutorial-hello-anchor.e2e.spec.ts`)

1. **Intro to finish**, at 1440x900: Start, q1 right, build fails on the
   planned E0412 ("E0412 · line 9"), "I'll fix it myself" and the fix
   question, build passes, win and Next; q2, deploy from a fresh wallet
   ("Create wallet", the program's Explorer link with `cluster=devnet`, the
   fake holding exactly that program); step 3's `client.ts` is created, a
   wrong q3 pick, then a **reload** reopens on the same question with that
   pick still ruled out, step 2's win in the feed and no intro; q3, run reads
   "Confirmed" with "Program log: Hello, World!"; q4, build and deploy reads
   "Upgraded" at step 2's program id, the call with the name "Alex" wins, and
   the finish card shows with no Next and its receipt log reads
   "Program log: Hello, Alex!".
2. **A wrong pick, then the right one**: q1's first wrong option is ruled
   out with "Not quite." and the definition's why, the build card waits, and
   the record ends "· 2nd try".
3. **The planned E0412**, with Explain: the card reads "E0412 · line 9" with the
   step's planned line; Explain posts the definition's explanation and the fix
   question (`/api/agent` answers "not configured", so no model is asked).
4. **The faucet at its limit**: the airdrop is refused, the red "Not enough
   devnet SOL" card shows with "Open faucet", and Try again under it deploys
   once the faucet answers.
5. **Step 3 passed from the Call panel**: `test.fixme` until HOO-2358 (#357)
   is in `scope/tutorial-flow`. Its body lists the scenario's steps and
   throws, so lifting the fixme without writing it fails.

Whole-run scenarios these specs leave out, covered by unit tests or still
open: a reload mid-deploy, the redeploy nudge after editing `lib.rs`, jumping
back from step 3, and funding with a build first.

## Testing plan

- `docs/testing.md` gets case **T-1**, the same walk on the real build server
  and devnet (`E2E_LIVE=1` runs spec 1 without the fakes).

## Steps

1. Fake build server and fake devnet, with spec 1 driving them red-to-green.
2. Specs 2 to 4 on the same fakes.
3. Spec 5 as `fixme`; T-1 in `docs/testing.md`.
4. `yarn run check`; the new spec locally (`test-e2e:with-stubs`), three runs
   in a row with no flake.
