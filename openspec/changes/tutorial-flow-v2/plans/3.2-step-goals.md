# 3.2 Step goals on real results — implementation plan

> For agentic workers: run with superpowers:executing-plans (inline). Steps
> use checkboxes.

**Goal:** a tutorial step passes only when a real result meets its goal
(`build`, `deploy`, `call`), and every pass fires `tutorial_step_passed`.

**Architecture:** the engine already asks a `Judge` port
(`model/ports.ts`) whether a result passes a goal; 3.1 shipped
`passingJudge`, which passes any `ok` result. This task writes the real judge
in `features/tutorial-conversation/model/goals.ts`, adds the facts a call goal
needs to the `run`/`call` result, and emits the event from the reducer's two
pass sites.

**Spec:** `specs/tutorial-runs/spec.md` "A step passes on what happened";
`specs/tutorial-conversation/spec.md` telemetry, `tutorial_step_passed`.
Ticket: HOO-1790.

## Global constraints

- `via` is `chat` (an act card), `client` (a client run) or `call_panel`;
  `step` is 1-based; `seconds` is the step's time.
- No step passes on the learner's word: there is no `read` goal.
- A call before the upgrade does not pass an argument goal.
- Layers: the feature imports `entities` and `shared` only; `views/` (legacy)
  may import `shared`.

## Decisions

- **Instruction names** compare through one helper,
  `shared/lib/idl-name.ts` `sameIdlName(a, b)`: case- and underscore-blind,
  since an IDL spells `greet_by_name` snake_case or camelCase depending on the
  Anchor version that wrote it. `views/flow/lessons/verify.ts`
  switches to it, which is the "reuse `VerifyCondition`'s logic" the task asks
  for without extending the lessons type.
- **What was called.** The `run`/`call` ok result gains
  `called: { instruction: string; args: Record<string, string> }[]`: each
  instruction the run's transactions invoked on the tutorial's program, with
  argument values as the *deployed* IDL decodes them. The log alone cannot
  tell a call before the upgrade: `Hello, World!` matches step 4's
  `Hello, .+!`. The client run and call act (4.3) and the Call panel (4.4)
  fill it; `parseResult` reads an unreadable or missing one back as `[]`.
- **Goals:**
  - `build`: an ok `build` or `buildDeploy` whose `instructions` hold every
    goal instruction.
  - `deploy`: an ok `deploy` or `buildDeploy`.
  - `call`: an ok `run` or `call` with an entry in `called` naming the
    instruction, every goal argument present with a non-blank value, and, when
    the goal has `log`, a picked `line` the pattern matches (unanchored,
    case-blind `RegExp.test`, as the schema says; an invalid pattern fails,
    reported once, rather than throws).
- `passingJudge` goes: its comment says 3.2 replaces it. Tests use
  `judgeGoal`.

## Review focus

1. A call whose argument is whitespace only — fails the goal.
2. A call result saved before `called` existed (no field) — parsed as no
   calls, so it fails, never throws.
3. A goal pattern the checker missed (invalid regex) — fails, never throws.
4. `greetByName` in the IDL against `greet_by_name` in the goal — passes.
5. A Call panel call on a win — passes nothing, no event (the reducer's
   rule; pinned by the once-per-step test).
