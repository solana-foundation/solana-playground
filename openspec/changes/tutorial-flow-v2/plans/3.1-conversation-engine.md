# Conversation Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> (inline) to implement this plan task-by-task. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** A headless engine walks a tutorial definition beat by beat, saves
the learner's progress in the workspace so project sync carries it, restores
it on reload with runs interrupted and never repeated, and emits
`tutorial_started` and `tutorial_finished`. Every card ticket (3.3 to 3.6) and
every run ticket (4.1 to 4.3) renders or feeds this engine's state.

**Architecture:** A new feature slice, `features/tutorial-conversation`, with
no React in `model/`. A pure reducer over the definition and the saved
progress produces the next progress and a queue of effects. A store,
`PgConversation`, is the one entry point: it loads the save for the open
workspace, dispatches, drains the queue through its ports (the workspace's
files, the runner and the judge), persists, and notifies. The feed's turns are a fold
over definition and progress, computed by `view`, so the save holds facts and
never copy. Three ports keep the engine headless: `Workspace` (read, write and
remove a file, like the assistant's `PlaygroundBridge`), `Runner` (build,
deploy, run, call, reporting stages and a result) and `Judge` (whether a
result meets a step's goal). The engine ships with in-memory
implementations for tests; the run tickets replace the runner's.

**Tech Stack:** TypeScript, vitest in-source blocks, the tutorial's storage
file at a full path resolved once from its name (`storagePath` in
`store.ts`), written with `writeWorkspaceFile`, `createTracker` for events.

**Spec:** `openspec/changes/tutorial-flow-v2/specs/tutorial-conversation/spec.md`,
"The lesson and the assistant share one thread" (progress, reload, Start over)
and "The conversation is measured" (`tutorial_started`, `tutorial_finished`);
`tutorial-runs/spec.md`, "A reload interrupts a run, never repeats it". Design
D2 and D3.

## Sources, and where they differ

The prototype (`almaz/mobile-tutorial-prototype`,
`design-system/src/prototype/tutorial-v2/store.tsx`, `check.ts`,
`landing.ts`, SPEC.md "State" and D28 to D30) is the model for the reducer's
actions, `flow()`, the write queue and `insertBlock`. The engine differs
where the app's shape forces it:

- **Files are not in the state.** The prototype's reducer holds `s.files`;
  here `PgExplorer` owns the files. The reducer reads a file's content only
  through the actions that carry it (`edit`, `written`) and writes only
  through the queue. The pure `insertBlock` is ported as is.
- **The thread is derived, not stored.** The prototype persists `thread: Turn[]`, copy included. The spec says the save holds facts, never copy, so
  `view` (below) rebuilds the turns from the definition on
  every read, and a fixed typo shows on reload.
- **Reload renders whole.** D28 types out only turns later than the page
  load; the spec says a reload renders turns whole with no typing or rise.
  Both agree in effect: a turn whose `at` is before the load has no
  animation. The engine marks it; the feed (3.3) obeys it.
- **Interrupted runs.** The prototype turns `running` acts into
  `interrupted` on load (SPEC "Persistence"). Kept, and the start time is
  saved so 4.2 can recognise a deploy that confirmed before the reload.

Decided here, no source settles it:

- **Who writes a block.** The engine, through the `Workspace` port, from its
  queue. The question card (3.5), Skip, "Show me the fix" and the typed-key
  fill all dispatch an action and never touch a file. `written` is dispatched
  only after the write lands, with the lines it took, so the save never
  claims a write that failed.
- **Who judges a goal.** A `Judge` port, `(goal, result) => boolean`. The
  engine's stub passes any `ok` result; task 3.2 supplies the real checks and
  replaces the stub where the store is wired.
- **Events.** The spec names `tutorial_started` and `tutorial_finished`, and
  the `tutorial` prefix belongs to `entities/tutorial`, so the two events are
  declared on that slice's tracker. The feature's own `model/telemetry.ts`
  exists, as `slice-structure.test.ts` requires, and re-exports it with the
  reason.

## Global Constraints

- The slice imports only `@/entities/tutorial` and `@/shared`, plus the legacy
  roots (`utils`) in `store.ts` and `real-workspace.ts` alone. Nothing imports `views/flow/lessons`,
  which task 7.1 deletes.
- Every reducer action carries `at`; the reducer never reads the clock,
  the file system or a global.
- The save is `.workspace/tutorial-storage.json` key `conversation`, written
  with `writeWorkspaceFile` at a full path resolved once from the tutorial's
  name, never through `PgTutorial.getStorage`, which resolves against the
  open workspace at write time. Its shape extends `ConversationSave` from
  `entities/tutorial/model/progress.ts` (`version: 1`, `passed`,
  `finishedAt`) without changing those three fields.
- A save whose `version` is not 1, or that fails `parseProgress`, or holds
  entries the parser drops, or names a step, beat or cursor position the
  definition no longer has, and a file that exists but could not be read,
  set `loadFailed`: the tutorial opens on the intro, the failure is logged
  and reported, the learner is told once, and the store refuses every write
  for that load except Start over, the learner's way out of it, so a real
  save is never replaced by a fresh one by accident.
- On load, a run saved as `started` becomes `interrupted`; nothing resumes.
- Start over writes a fresh save; the assistant's thread is untouched.
- No write to the lesson's files except through the `Workspace` port, and
  none for a `say` beat.
- Conventional Commits, scope `client-v2`, ticket `HOO-2350` in the subject.

## Decisions this plan takes

The types in `model/progress.ts`, `model/ports.ts`, `model/reducer.ts` and
`model/view.ts` are the source for every shape below; this section says what
they decide and why. (Rewritten after the sx review of 29 Oct to what
landed.)

- **Save shape** (`ConversationProgress`): the card's three fields
  (`version: 1`, `passed`, `finishedAt`) plus `startedAt`, a `cursor`
  (`intro`, a step with its next beat index and whether it is in `onFail`,
  or `finished`), `beats` (every reached beat's `Resolution`, by id), `runs`
  (every run of each act, by beat id, **a list oldest first**: a run again
  keeps the earlier run as its card in the feed) and `times` (each step's
  `from`, `to` and the `via` it passed by). A resolved question keeps
  `openedAt` beside its resolve time, so its card keeps its place in the
  feed; `hintedAt` is when the hint was asked; `wrote` is the lines its
  answer took once the write landed; `writeFailed` says the write did not.
  A failed run carries `planned: true` when it was the step's planned
  failure, judged once when it ended. A question left open when its step
  passes from elsewhere is `skipped` with `via: "elsewhere"` (or
  `call_panel`): no block is written and no Skip line posts, so it never
  reads as the Skip button, which is the only skip the `skip` action
  records. `restartedAt` is when Start over last reset the save: the
  assistant's thread is kept, and 3.6 shows only its exchanges after that
  moment. Copy is never saved.

- **Actions** (`Action`): `start`, `pick`, `hint`, `skip`, `typeIt`, `edit`
  (file and its content), `written`, `writeFailed`, `act` (an act beat
  pressed, or its composer word), `stage`, `ended`, `passed` (a goal met
  from the Call panel or a client run), `explain`, `fixMyself`, `next`,
  `finish`, `startOver`. `load` is the store's, not an action: it parses
  the save. `stage` and `ended` carry the run's `startedAt`, echoed from
  the `run` effect, so a stale run's answer is dropped. `next` on the last
  win is a no-op: the store dispatches `finish` at `view.finishAt`, the
  win plus `FINISH_DELAY_MS`, and that emits `tutorial_finished`. "Show me
  the fix" after an unplanned failure is task 4.1's, with the assistant's
  answer it follows. There is no `tick` action: a turn's `at` is data.

- **The planned failure**: a failed build with a parsed compiler error, on
  a step with `onFail`, before the cursor has entered it. A run that could
  not happen (`error: null`) is never planned, so a missing runner or a
  network error cannot impersonate the lesson's scripted mistake. Once in
  `onFail`, a later failed build is an ordinary failure whose result card
  stays open. `fixMyself` enters `onFail` at its first non-`say` beat.

- **The queue** (`Effect`): `write` (block, file, the typed key line for a
  fill, and `at`), `create`, `run` (act, `RunInput`, `startedAt`), `event`,
  `focus` (a file and a line, or the landing), `explain` (an unplanned
  failure for the assistant) and `restore` (whole files to put back and
  files to take away: the first step's start on Start, with the preview's
  files no step holds removed; the intro's preview on Start over, with the lesson's
  other files removed; so the workspace swaps as the spec says and a second
  run of the lesson writes over clean files). The store drains them in order: a write
  reads the file, places the block with `insertBlock` and writes it, then
  dispatches `written` with the lines, or `writeFailed` when it could not;
  a run goes to the `Runner` and comes back as `stage` and `ended`.
  `insertBlock` keeps the block's own lines where it lands, so a learner's
  `msg!` words reach the file.

- **`view(definition, state, { now, loadedAt })`**: the turns in order by
  `at` then construction order, each `whole` when older than the load, and
  only those whose `at` has come; the live card; the step bar; the
  composer's placeholder; `nextAt`, the earliest turn still ahead, and
  `finishAt`. The store re-renders at `nextAt` and dispatches `finish` at
  `finishAt` with one timer, and persists only when the save changed, never
  on a stage. The feed never computes any of this itself.

- **The clock** (`model/clock.ts`): two constants. `TICK_MS` is the
  prototype's queue cadence: each scripted turn arrives one tick after the
  one before. `FINISH_DELAY_MS` is the spec's 400 ms.

- **Ports** (`model/ports.ts`): `Workspace` (`read(path, workspace)`,
  `write(path, content, workspace)`, `remove(path, workspace)`, nothing to
  do when there is none: the real port refuses any workspace but the one
  the effect was queued for, checked in the same tick as the path
  resolves), `Runner` (`run(act, input, onStage)` with
  `RunStage { label, index, count }`, resolving a `RunResult` and never
  throwing), `Judge`. `memoryWorkspace`, `stubRunner` and `passingJudge`
  are for tests; `unwiredRunner` resolves a failed result and is never the
  store's default, since `init` requires a runner. `failedResult(act, message)` shapes a run that could not happen.

- **`PgConversation`** (`model/store.ts`): `state`, `view(now)`,
  `onDidChange`, `onDidRequestFocus`, `onDidRequestExplain`, `init(ports)`
  subscribing to workspace switches, one method per action, `_dispatch`
  persisting after every change to the save, the `loadFailed` guard, one
  toast per tutorial when the load failed and one when a save fails. The
  save is read and written at a full path resolved once from the tutorial's
  name (not through `PgTutorial.getStorage`, which resolves against the
  open workspace at write time), one write at a time per tutorial. Entries
  the parser drops are logged and reported by key and fail the load, so
  they are never written back without. The same workspace opened again
  while an act runs (a sync pass re-opens it) is not reloaded, and a reload
  waits for a save of that tutorial still in flight. An act is explained or
  fixed only while its step is the cursor's and not passed, and a run again
  of an act the flow already went past posts nothing; the view keeps the
  card of an act whose ok result the goal refused as the live one. A save the engine cannot read,
  or one naming a step or beat the definition no longer has, is a failed
  load: the intro shows, the failure is logged and reported, and nothing
  is written until Start over, the one write allowed over it. A load that
  lands after a workspace switch is dropped.

- **The real workspace** (`model/real-workspace.ts`): reads through the
  explorer, writes through `utils/explorer/apply-file.ts`, the two-step
  write (explorer, then the open Monaco model) extracted from the
  assistant's bridge so both share it, and removes through
  `PgExplorer.deleteItem`. A `WorkspaceMovedError` from it is an expected
  race the drain logs as a warning, never a reported error.

## Review Focus

- A reload during `flow()`: turns already past render whole, the one not yet
  arrived still arrives at its `at`, once (Task 3).
- A write that fails: the drain goes on, the question stays resolved with
  `writeFailed` and no `wrote`, one `log.error`, and the card says the block
  is not in the file (Task 4).
- A `pick` on a resolved question, an `act` while another runs, `next` with
  no live win: the same state object back (Task 2).
- `ended` arriving after Start over or a workspace switch: dropped, since
  its `startedAt` is not the current run's, or the workspace moved; either
  way the drain logs it, and reports a landed deploy (Task 5).
- The card's two fields, `passed` and `finishedAt`, keep their shape; the
  progress test pins them without calling `conversationProgressOf`, whose
  barrel loads UI (Task 1).
