# 4.4 The Call panel from the deployed IDL

Ticket: HOO-2358 "Tutorial Call panel built from the deployed IDL". Uses the
run and call of task 4.3 (`runOnDevnet`, `Runner`) and the Call slot of task
2.2 (`TutorialWorkspace`'s `call`).

## Success metric

Some learners pass step 3 from the Call panel. Check:
`tutorial_step_passed` with `via: "call_panel"` in the first week after
Breakpoint.

## Design gaps (decided, checked with Design alignment on 5 Nov)

The look is Almaz's tutorial-v2 prototype (`ui/TestForm.tsx`, 31 Oct). An
umbrella task leaves the specs and `design.md` alone, so where they differ this
plan holds until the PR that closes the change.

1. **No program row.** Answer 3.21 and the spec ask for one; the later
   prototype has only Form | IDL at the head and the program in the heading,
   with the Explorer link in the result's quiet details row. The prototype wins.
2. **The chip picked on open:** the live step's own instruction when its goal
   names one, else the latest added.
3. **The result is the prototype's, not the conversation's card:** the status
   alone, no instruction named, so the ticket's "instruction in its meta" is
   overruled. Its sentence is the prototype's, "The call used {n} compute
   units", not the runs spec's "It used". Another chip shows no result; the
   same chip with moved fields dims it under "Last call, with name "Ada"". One
   from before the latest deploy goes. While a call goes the button reads
   "Calling" and the response "Sending"; Call is also off while an act runs.
4. **Accounts are not asked.** The Test form's default generators fill them;
   `fillRandom` never does. The addresses earlier calls wrote to
   (`progress.accounts`, HOO-2505 Repeating call card) fill theirs. An account
   neither leaves empty keeps Call off with a note over the button.
5. **`call-form` is not installed.** The design system's component lives only
   on `almaz/mobile-tutorial-prototype`, with a different `Segmented` and
   `Button`. `BaseCallPanel` is built from the parts on this branch, to its
   layout. The `msg!` source beside the program's words is left out.

## Where state lives

- **The deployed IDL:** `deployed` in the saved progress, one writer, so project
  sync carries it with the program and Start over clears it. A deploy's result
  carries its IDL into the reducer, which moves it out of the run's record.
  Never written on a build.
- **Seen (the dot and "New"):** one device's `localStorage`, by tutorial, as
  the docked tree is, so opening the panel never reads as a change elsewhere.
- **Open, tab, picked chip, form values:** the tab's `sessionStorage`, by
  tutorial, so a reload finds the panel as the learner left it ("Reload in
  step 3"). Not `.workspace/metadata.json`: nothing of it syncs. The latest
  result stays in memory, for the visit.
- **Who writes `deployed`:** only a deploy card. A deploy from the terminal
  moves nothing until the card runs, which step 2 and the upgrade step ask for
  anyway; a call in between fails with "Build and deploy it again".
- **A card during a panel call:** the panel waits for cards, not the other way
  round. A card pressed mid-call reports the capture as busy and can be pressed
  again.

## Steps

1. `model/deployed-idl.ts` (pure): `addedNames`, `shapeOf`, `nextDeployed`,
   `parseDeployed`.
2. Reducer: `ended` and `recognised` keep a deploy's IDL in `deployed`; `act`
   and `panelInput` give runs `input.idl`; `passed` with `via: "call_panel"`
   emits `tutorial_action_run` with `action: "call_panel"`, whether or not the
   step passes.
3. `real-deploy.ts`: a deploy that lands, or is recognised, carries
   `PgProgramInfo.idl`.
4. `real-run.ts`: `sendCall` and `decode` use `input.idl`;
   `PgProgramInteraction.test` takes the program to send through.
5. `PgConversation.callFromPanel`: the port's runner, then `passed`.
6. `model/call-view.ts` (pure) and `model/call-panel.ts`: `PgCallPanel`, its
   state, the dot and "New" per device, the log to the terminal.
7. `widgets/tutorial-workspace`: `BaseCallPanel`, `CallPanel`, `CallButton`, the
   panel over the stage, closed by opening a file.
8. `TutorialConversation`: `openCall` opens the panel.

## Verify

`yarn run check`; in-source tests for steps 1, 2 and 5; `BaseCallPanel.test.tsx`
for the upgrade adding `name`, "Several instructions" and the disabled states;
a store test for a call passing step 3; a screenshot of the panel against the
