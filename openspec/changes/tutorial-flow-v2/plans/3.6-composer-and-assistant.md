# Composer and Live Assistant Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> (inline) to implement this plan task-by-task. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** One composer under the tutorial feed. A live action's word runs
that action, a finish chip posts its definition answer, and anything else
goes to the product's assistant, which answers in the same feed and, in a
tutorial, never writes or runs anything itself.

**Architecture:** Three parts, kept apart by the layers (design D2, D3).

- **The engine** (`features/tutorial-conversation`) gains the composer's
  records as progress facts: the word pills, the open-question refusal, the
  finish-chip exchanges and the apply card's proposals with their
  Apply/Keep state. It also gains the pure routing of a typed message.
- **The assistant** (`views/sidebar/assistant`, a legacy root) gains one
  seam, a tutorial mode on `PgAssistant`. The mode adds a context message,
  replaces the tool set, and refuses a call it does not allow. The assistant
  never imports the tutorial feature.
- **The widget** (`widgets/tutorial-conversation`) sets that mode while it is
  mounted, with its four interface tools; merges the assistant's thread into
  the feed at render; and draws the composer, the assistant's turn and the
  apply card. `views/flow/Flow.tsx` mounts the assistant's turn runner
  (`useTurn`) while the tutorial frame shows, since a widget may not import
  `widgets/assistant`.

**Tech Stack:** React 19, Tailwind 4, `shared/ui` (`composer`, `diff`,
`button`, `tag`), the AI SDK through `shared/lib/ai`, vitest in-source blocks
and Testing Library.

**Spec:** `openspec/changes/tutorial-flow-v2/specs/tutorial-conversation/spec.md`,
"One composer; free questions go to the live assistant" (scenarios "A free
question", "Typed I'm stuck", "Change what hello says"), "The lesson and the
assistant share one thread" and the `tutorial_question_asked` event. Linear
HOO-2354.

## The base this builds on (3 Nov)

`scope/tutorial-flow` at `f6e0e705`, plus task 3.4 (PR 248, in review), which
this branch is stacked on:

- **3.5, the question card, landed** (#258). `BaseQuestionCard` resolves
  picks, Hint, Skip and "Type it myself" through `PgConversation.hint`,
  `skip` and `typeIt`. The card takes the focus as it arrives, unless a text
  field holds it (`typing`), and its keys work only while the focus is on the
  card or on nothing. So a learner typing in the composer keeps the field,
  and the composer's keys never reach the card.
- **2.2, the workspace, landed** (#237). `widgets/tutorial-workspace` owns the
  tabs, the docked tree and the terminal bar, and `Flow.tsx` passes it the
  feed's `marks`. It is a widget, so the open files for the assistant's
  context are read from the editor (`PgExplorer`), not from it.
- **4.2's runner landed, the task is still open** (#241). A deploy act now
  runs for real (`tutorialRunner`, `actRunner`), so "deploy" as a typed word
  runs a real deploy. Build (4.1) and the client run (4.3) are not wired yet.
  The redeploy nudge is still unbuilt and stays 4.2's.
- **The engine gained `interrupted` and `recognised`**, and deploy results
  now carry `lamports: number | null` and a `no_funds` failure with its
  balance, cost and address. The "last result" in the assistant's context is
  the engine's last run record, whatever its act.

## Sources, and where they differ

- **Records live in the engine save** (Natalia, 2 Nov). Word pills, the
  refusal, chip exchanges and proposals are new progress facts and actions;
  Apply writes through the `Workspace` port, so it gets a wrote card. Only the
  assistant's own text stays in its chat thread. Chat item kinds are pinned by
  `messages_kind_check`, so a new kind there would cost a migration. This sets
  the version policy HOO-2350 deferred: **an added field is optional, and an
  absent one parses as empty**; `version` stays 1.
- **Tutorial mode is a seam on `PgAssistant`** (Natalia, 2 Nov):
  `{ name, context(), tools, allows(name), refusal }`, set by the widget. `createTools`
  filters by it, and a disallowed call is refused rather than run.
- **The turn runner is mounted by `Flow.tsx`** (Natalia, 3 Nov). The tutorial
  frame does not draw the assistant column (`BaseLayoutShell`), so nothing
  subscribes to `PgAssistant.onDidRequestPrompt` with `sends: true` there.
  `Flow.tsx` calls `useTurn` while the frame shows (`TutorialChat`) and
  hands it to the composer, which sends with the turn's own `send`, so text
  the turn puts back (no model connected) lands in the tutorial's box.
- **The composer is mounted in this PR** (Natalia, 3 Nov). HOO-2509 (mount the
  feed, canceled once the feed mounted itself) says a later piece "mounts
  itself in this slot", and `Flow.tsx` leaves the slot to 3.6.
- **Before Start the composer waits, and suggests starting once answered**
  (the designer, 3 Nov; the spec change approved by Slava, 4 Nov). The
  placeholder reads "Ask anything about this tutorial", the composer is not
  greyed (Design alignment, 6 Nov) and takes a question or a start word, and
  once the assistant has answered a question, the composer suggests "Ready to
  start the lesson?" with a "Start step 1" button, which lifts on Start. The
  suggestion is drawn by the composer, not asked of the model, so it is
  always there and never phrased differently.
- **The design audit of 3 Nov** (Slava, on HOO-2354, from Almaz's prototype
  at `f7d42bf2e`): the composer is one 44 px row with a 22 px line and Send
  beside the words; "Or ask about this step" while a question is open; and
  the failed build's "Explain the error" and "I'll fix it myself" take one
  width on a wide pane, stacked on a phone. Missed in the first round and
  raised by the PR review (ocatave, 4 Nov); fixed in the same PR. Checked
  against the prototype's own code afterwards: the field is one line only at
  rest and opens to the full box once focused or holding text, folding only
  after a press ends; Send keeps `brand-action` with a grey disabled state
  and a 44 px touch size; "Ask while it runs" for a run or a call; and a
  phone does not offer "I'll fix it myself". The prototype's story prompt
  ("Type what hello should say") has no counterpart: the definition has no
  story, and the finish is not reachable yet.
- **A question counts once the assistant has it** (the PR review, 4 Nov):
  `useTurn`'s `send` says what became of the message (`SendOutcome`), and
  `tutorial_question_asked` fires on `sent` only, not when the message
  opened Connect a model or waited for an answer.
- **Chips match on a press only**, never on typed text: the spec's "no
  scripted answers matched from typed text" (Almaz, 3.17, 28 Oct). Routing a
  typed message is therefore words, then the assistant; a chip is its own
  path.
- **Typed "I'm stuck" goes to the model**, which calls Hint. The Hint tool
  calls `PgConversation.hint`, the question card's own path, so the hint
  posts on the card as if H was pressed, and no "I'm stuck" pill posts, since
  the typed message already shows. Skip does the same through
  `PgConversation.skip`.
- **With no model connected**, a free message routes to connecting one: the
  text stays in the composer and the connect dialog opens, as the panel's
  `useTurn` already does. An action word and a chip need no model.
- **The doc list** goes into the context from `definition.docs`. Opening a doc
  as a tab is HOO-2381; the assistant only names or links the page.
- **The redeploy nudge** after applying to a deployed file is `tutorial-runs`'
  (task 4.2). This PR applies and posts the wrote card only, with
  `TODO(tutorial-flow-v2 4.2)` where the nudge goes.
- **The existing lesson context** (`bridge/lesson-context.ts`,
  `describeLesson`) reads the v1 `PgLesson`. In tutorial mode the mode's
  `context()` replaces it; the v1 path is unchanged.

## Telemetry (confirmed by Natalia, 3 Nov)

- `tutorial_question_asked` `{ tutorial, step, source: "typed" | "chip" }`, in
  the spec. No question text.
- Added beyond the spec (its delta gets them in Task 7):
  - `tutorial_word_sent` `{ tutorial, step, word, refused }`, when a typed
    action word runs or is refused while a question is open;
  - `tutorial_change_applied` `{ tutorial, file }` and `tutorial_change_kept`
    `{ tutorial }`, for the apply card.
- The assistant's own events (`assistant_*`) fire as they do in the panel.
- Logs: `tutorial-conversation:mode`; the engine's under its existing
  namespace, and the mode's context failures under `assistant:provider`.

## Tasks

### Task 1: The records in the save

- [x] Add to `ConversationProgress`:
  - `said: Said[]`, oldest first: `{ kind: "word" | "refused"; text; at }`
    and `{ kind: "chip"; index: number; at }`;
  - `proposals: Proposal[]`: `{ id, file, line, before, after, at, state:
    "open" | "applied" | "kept", settledAt?, applyFailed?: "moved" | "write" }`.
- [x] `parseProgress`: an absent list reads as `[]`; a malformed entry is
  dropped and reported through `onDrop`, like `parseReceipt`'s neighbours.
- [x] Reducer actions `word` (its pill, then the action it names),
  `refuseWord`, `chip`, `asked` (counted only), `propose`, `apply` (an
  `apply` effect the store carries out through `Workspace`, refusing a line
  that moved since), `applied`, `applyFailed` and `keep`. A settled proposal
  does not move again. The wrote card is drawn from the applied proposal.
- [x] `restartStep` keeps the records; `startOver` clears them (the thread is
  kept and filtered by `restartedAt`).
- [x] Tests: parse of an old save (no fields), reducer cases for each action,
  apply's wrote card and its failure.

### Task 2: Routing

- [x] `wordOf(text)`: "build", "deploy", "run", "call", "next", "explain",
  and the intro's "start", "begin" and "go" (the spec's "A tutorial opens on
  its intro card"), alone or with "please", any case and trailing
  punctuation; anything else is null.
- [x] `route(text, live)`: a word whose action is live → `action`; a word
  while a question is open → `refused`; anything else → `assistant`.
  A word with no live action goes to the assistant.
- [x] In-source tests for the order (the ticket's happy path) and for "please
  build", "Build!", "build it" (→ assistant).

### Task 3: The tutorial mode seam

- [x] `PgAssistant.setMode(mode)` (modes stack; its `dispose` removes that
  one, leaving the latest other in force) and `mode`;
  `AssistantMode = { name, context(), tools, allows(name), refusal }`.
- [x] `createTools`: with a mode, keep the tools `allows` names (the tutorial
  allows `READING_TOOLS`: `list_files`, `read_file`, `get_build_error` and
  the skill tools `list_skills`, `load_skill`, `read_skill_reference`) and
  add the mode's own; any other call is refused with the mode's `refusal`,
  which the model reads, and logged.
- [x] `provider.ts`: the mode's `context()` joins the per-turn system
  messages.
- [x] Tests: "a write-file tool call is refused in tutorial mode" (the
  ticket's edge case); no mode, the tool set is unchanged.

### Task 4: The widget's mode

- [x] `mode.ts`: tools `open_menu`, `hint`, `skip`, `propose_change`
  (`file`, `line`, `after`). Each does only what the lesson's own control
  does: the menu overlay, `PgConversation.hint` / `skip` on the live
  question, `PgConversation.propose`. With no live question, Hint and Skip
  return a refusal the model reads.
- [x] `context()`: the tutorial, the step and its objective, the open files
  (from `PgExplorer`), the last run record and the doc list
  (`definition.docs`), built by the pure `describeTutorial` in
  `model/context.ts`. The hint tool posts with `byAssistant`, so no "I'm
  stuck" pill repeats the learner's message. `Flow.tsx` hands the feed
  `onOpenMenu`, the frame's `nav.onOpenChange(true)`.
- [x] `TutorialConversation` sets the mode on mount and clears it on unmount.
- [x] Test: "Typed I'm stuck" (the model calls `hint`, the hint posts, the
  question stays open). `model/mode.store.test.ts` runs the hint tool against
  the real engine; the composer's routing of "I'm stuck" to the assistant is
  `TutorialComposer.test.tsx`'s; the browser check ran the whole path with a
  stubbed model.

### Task 5: The merged feed

- [x] `mergeFeed(turns, items, since, loadedAt)` (`model/merge.ts`): the

  empty streaming reply waits for its words, errors and notices show as the

- [x] The live card stays the lesson's: an exchange never takes `live`.
- [x] The composer's records as turns (`view.ts`, `composerTurns`): the word
  pill, the refusal's pill and `PICK_FIRST`, a chip's label and answer (a
  `reply` turn with its `follow`), the apply card, and its wrote card at

- [x] `BaseFeed` takes the merged `entries` and `renderExchange`;
  `BaseAnswer` draws a reply through `components/Markdown`, with no bubble.
  `BaseApplyCard` draws the diff with "Apply to <file>" and "Keep it".
- [x] Tests: ordering, the restart filter, whole-on-reload, the records'
  turns, the apply card's buttons and states, and the feed showing an
  exchange as it streams in.
