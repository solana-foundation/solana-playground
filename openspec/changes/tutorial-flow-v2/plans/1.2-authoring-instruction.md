# 1.2 Authoring instruction: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Goal:** `client-v2/src/tutorials/AUTHORING.md`, the instruction an agent
follows with only it and `tutorial.schema.json` in hand to turn a
conversation with a product person into a `tutorial.json` that passes
`yarn tutorial:check`.

**Architecture:** One Markdown file beside the schema. Its JSON examples are
checked by a test, so it cannot drift from the format: beat examples must
equal a beat in Hello Anchor's definition, and the worked example is a whole
definition the check accepts. A fixture written by a fresh agent from the
instruction alone proves it works, and a generic walker drives that fixture
through the conversation engine from the intro to the finish.

**Tech stack:** Markdown, vitest, the check (`checkDefinition`) and the
engine (`PgConversation`) from task 1.1 and 3.1.

**Spec:** `openspec/changes/tutorial-flow-v2/specs/tutorial-definition/spec.md`,
"An agent can write a tutorial from the authoring instruction".

## Global constraints

- Self-contained: the instruction names no repository path an LLM would have
  to open, except where it tells the author's agent what to run in a clone.
- Publishing is by pull request that adds the tutorial's folder; there is no
  admin panel and no upload service.
- Steps: one to six; four to six for a published tutorial.
- Voice: two to four sentences a message, one rich block at most, three
  options with a reason for each wrong one, a win per step.
- Everything committed is English.
- The format is v1 as merged (HOO-1792). Where a script needs what v1 cannot
  say, the instruction says stop and report; it never invents a field (Lead,
  2 Nov: the format gaps for Lumberjack and Zero Copy went to Planner).

## Review focus

1. A beat example in the instruction that no longer matches Hello Anchor
   after someone edits the definition: the test fails and names the beat.
2. A block whose lines appear twice in the target (`}` lines): the
   instruction says a block lands at its first match and how to make it
   unique.
3. A step whose `start` is not the previous step's `target`: the
   instruction says to copy it, since the engine rebuilds files from the
   target and drops lines it does not know.
4. A `name` whose slug is not the folder name: the check's error is
   explained.
5. Opening the tutorial in `yarn dev` before the feed (task 3.3) lands: the
   instruction says what the author sees today (listed in the catalog) and
   what proves the run (the check, then a reviewer).

### Task 1: AUTHORING.md and the test that keeps its examples true

**Files:**
- Create: `client-v2/src/tutorials/AUTHORING.md`
- Create: `client-v2/src/tutorials/authoring.test.ts`

**Interfaces:**
- Consumes: `checkDefinition(json, known, { slug, docs })` and `formatError`
  from `@/entities/tutorial/model/definition/check`; Hello Anchor's
  `tutorial.json`.
- Produces: the fenced blocks the test reads. A block fenced
  ` ```json beat ` is one beat of Hello Anchor; the one block fenced
  ` ```json tutorial ` is a whole definition whose `name` slug is its
  folder in the example.

Sections, in this order: what you hand over (the two files); the questions
to settle first; the shape of a definition; the steps and their files; the
four beats, one Hello Anchor example each, and the planned failure; goals
and wins; the finish and docs; the voice rules; a worked two-step example;
from a prototype script (Almaz's `lessons/*.ts`); running the check and
reading every error it prints; trying it locally; the pull request.

- [ ] **Step 1: Write the failing test** `tutorials/authoring` in
  `authoring.test.ts` (its own file: it reads a file from disk):
  - `every beat example is a beat of Hello Anchor`: each ` ```json beat `
    block parses and `toEqual`s the beat of the same `id` in Hello Anchor's
    steps (beats or `onFail`); at least one block of each kind `say`,
    `write`, `ask`, `act`.
  - `the worked example passes the check`: the ` ```json tutorial ` block
    gives `checkDefinition(json, new Set(), { slug: slugOf(json.name) })`
    `toEqual([])`, and has exactly two steps.
  - `quotes the line the check prints for: <break>`: each error the section
    explains is made by breaking the worked example one way and running the
    check, and the printed line is quoted verbatim; no quoted line is one the
    check does not print. The missing reason prints
    `steps[0].beats[2].why[2]: a wrong option needs a reason, found null`.
- [ ] **Step 2:** `yarn test-unit src/tutorials/authoring.test.ts` fails
  (no AUTHORING.md).
- [ ] **Step 3:** write `AUTHORING.md`.
- [ ] **Step 4:** the test passes; `yarn check-md` and `yarn check-format`
  pass.
- [ ] **Step 5:** commit `feat(tutorials): the authoring instruction an agent
  follows to write a tutorial (HOO-2347)`.

### Task 2: a fixture from the instruction alone, walked through the engine

**Files:**
- Create: `client-v2/src/tutorials/__tests__/<slug>/tutorial.json`, written
  by a fresh subagent given only `AUTHORING.md` and the schema in an empty
  folder, on a topic other than the worked example's. Committed as it came
  back; if it fails the check, the instruction is fixed and the agent re-run,
  never the JSON by hand.
- Create: `client-v2/src/features/tutorial-conversation/model/walk.test.ts`

**Interfaces:**
- Consumes: `PgConversation` (`init`, `start`, `pick`, `act`, `explain`,
  `next`, `view`, `state`), `memoryWorkspace`, `stubRunner` from `./ports`;
  the mocks `engine.test.ts` uses.
- Produces: `walk(definition)` inside the test file: answers every `ask` with
  its `answer`, presses every `act` (a call act with `"x"` for each arg),
  fails the first build of a step that has `planned` and then `explain`s,
  presses Next after each win; the stubbed runner returns an ok result of the
  act's kind, and the judge matches kinds only (`goals.ts`, HOO-1790, judges
  `log` and `args`).

- [ ] **Step 1:** run the subagent; `yarn tutorial:check
  src/tutorials/__tests__/<slug>` prints `<slug>: ok`.
- [ ] **Step 2: Write the failing test** `passes the check` and `walks from
  the intro to the finish`: the fixture passes `checkDefinition`; after
  `walk`, every step passed, `finishedAt` is set, at each win the step's
  files equal its target (trailing whitespace aside), no error was logged and
  no toast shown. The same walk over
  Hello Anchor passes too, so the walker is not shaped to the fixture.
- [ ] **Step 3:** the walker; the test passes.
- [ ] **Step 4:** commit `test(tutorials): a fixture written from
  AUTHORING.md alone runs from intro to finish (HOO-2347)`.
