# 4.1 Build act and the planned failure: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (inline). Steps use `- [ ]`.

**Goal:** A tutorial's build act compiles on Playground's build server. Hello
Anchor's first build fails with E0412 at line 9, which turns into the planned
explanation and fixing question. An unplanned failure goes to the assistant,
followed by "Show me the fix".

**Architecture:** A `runBuild` act runner runs the editor's `build` command and
reads the raw log the command keeps (`PgBuildOutput`). A pure picker chooses
the error to show from `parseBuildReport`'s diagnostics. The step's new
`failsWith` line decides which failure is the planned one. The engine
(3.1) already holds the planned and unplanned paths. This task adds the
unplanned follow-up, the say turn with "Show me the fix" and its one write. It
also adds the unreachable card to 3.3's result card.

**Tech Stack:** TypeScript, React 19, vitest (in-source and Testing Library).

**Spec:** `specs/tutorial-runs/spec.md` "Build runs on Playground's build
server"; `specs/tutorial-conversation/spec.md` "A failed build explains
itself"; `specs/tutorial-definition/spec.md` (`failsWith`); `design.md` D4.
Ticket HOO-2355 (refreshed 2 Nov, with the spike and the design gaps).

## Global Constraints

- Copy:
  - "Build server unreachable"
  - "Build couldn't start. The Playground server didn't answer. Your code is unchanged."
  - "Try again"
  - "Show me the fix"
  - "Fix it in the editor and build again, or I can show you the lines this step needs."
- Test fixtures are the real server logs from the 2 Nov spike: the planned
  E0412, a failure with no code, and a pass. They are kept verbatim,
  including the `Error: Function … Stack offset` noise and the uuid paths.
- No new telemetry event. `tutorial_action_run` is declared and fired from the
  reducer for every act by 4.2 (#241, HOO-2356), agreed with that session on
  3 Nov. Whichever PR merges second plugs `build: runBuild` into its
  `actRunner`.
- The editor's error line and the terminal's auto-open are 2.2's
  (#237, HOO-2349). This task only makes the line they mark the picked error.

## Review Focus

1. The first error is a macro symptom (E0432 at line 5). The card must show
   E0412 at line 9. _Task 2._
2. A server that answers 500, such as "Invalid path", is not "unreachable".
   It shows the log with no line link. _Task 4._
3. A build output from another workspace, or from before the press, is never
   read as this run's. _Task 4._
4. A save written before `reason` existed still loads; a failed build without
   it reads as `compiler`. _Task 3._
5. "Show me the fix" pressed twice writes once. _Task 6._

### Task 4: the build runner, wired

**Files:** create `model/runners/build.ts` (`runBuild`) and `model/runners/build.test.ts`
(it calls `vi.mock` on `@/utils`'s `PgCommand` and the `PgBuildOutput` bridge).
Modify `index.ts` (export `runBuild`) and
`widgets/tutorial-conversation/ui/TutorialConversation.tsx`: the runner sends
`build` to `runBuild` and the rest to `unwiredRunner`, with a
`TODO(tutorial-flow-v2 4.2)` that #241's `actRunner` replaces it.

**Produces:** `runBuild(act: Act, input: RunInput, onStage): Promise<RunResult>`.

1. It calls `onStage({label:"Building", index:1, count:1})`.
2. It notes `t0` and `ws`, then `await PgCommand.build.execute()`.
3. If that throws, it checks the message:
   - a network message (`/Failed to fetch|NetworkError|Load failed/`) gives
     `failedResult("build", …)` (unreachable);
   - anything else gives `{reason:"compiler", error:null, log:message}`.
4. It then requires `PgBuildOutput.latest` with `at >= t0` and
   `workspace === ws`. Without one, it gives unreachable.
5. A failed output gives
   `{reason:"compiler", error: pickBuildError(stderr, input.failsWith), log: stripKnownNoise(stderr)}`.
6. A good output gives `{ok:true, instructions: PgProgramInfo.idl?.instructions.map(i => i.name) ?? []}`.

`seconds` is the time from `t0`.

- [x] Tests:
  - A pass gives `["hello"]`.
  - The planned log gives E0412 at line 9.
  - Fetch failed gives unreachable.
  - "Invalid path" gives compiler with the log.
  - A stale output (an `at` before the press, or another workspace) gives unreachable.
- [x] FAIL, then implement, then PASS. Commit.

### Task 6: unplanned Explain, then "Show me the fix"

**Files:**

- `model/progress.ts`: a failed `RunRecord` gains `explainedAt?`,
  `answeredAt?` and `fixedAt?` (numbers), parsed when they are numbers.
- `model/reducer.ts`:
  - `explain` on an unplanned failure stamps `explainedAt` and keeps the
    `explain` effect;
  - a new action `{type:"answered"; beatId; at}` stamps `answeredAt` once,
    only after `explainedAt`;
  - a new action `{type:"showFix"; beatId; at}` acts only once, only after
    `answeredAt`, and only while the step is not passed. It stamps `fixedAt`
    and queues `restore` with `{[step.file]: step.target[step.file]}`.
    The widget shows the first line that changes (`firstChange`); lighting every written line is left to the workspace's marks.
- `model/view.ts`:
  - after the result card, a `you` turn EXPLAIN at `explainedAt`;
  - at `answeredAt`, a `say` turn with the Global Constraints' fix line and
    `follow: { kind: "showFix", done }`, done once fixed, the step passed, or a later run exists;
  - the result is not `open` once explained.
- `store.ts`: `PgConversation.answered(beatId)` and `showFix(beatId)`.
- Widget:

  - `TutorialConversation` subscribes `onDidRequestExplain`. It sends
    `PgAssistant.requestPrompt(<error line, location, log>, {send:true})`
    and dispatches `answered` when the assistant's turn ends, or at once when
    `!PgAssistant.isConnected`.
  - `BaseSay` draws the follow as an outline `sm` button, disabled once
    done.

- [x] Tests:
  - Reducer: explain, answered, showFix writes the step file's target, and a
    second showFix does nothing.
  - View: the turns are in order.
  - Component: pressing "Show me the fix" calls `showFix`, and the button
    is disabled after it.
- [x] FAIL, then implement, then PASS. Commit.
