# 4.2 Deploy from the learner's wallet — implementation plan

> For agentic workers: run with superpowers:executing-plans (inline). Steps
> use checkboxes.

**Goal:** a tutorial's deploy act deploys the last build to devnet from the
learner's Playground wallet, funds the wallet itself when it is short, keeps
the program's address so a later deploy upgrades it, and reports every fact
the result card needs: cost, program id, signature, upgraded.

**Ticket:** HOO-2356. **Spec:** `specs/tutorial-runs/spec.md` "Deploy goes
from the learner's wallet on devnet", "A reload interrupts a run, never
repeats it", "Runs are measured"; design D4, D6.

## Success metric

At least 9 of 10 first deploys in the dry run land, counting a learner who
funds the wallet from the faucet card and presses Try again. Check:
`tutorial_action_run` deploy outcomes, 9 Nov. (Was: without leaving the
tutorial to fund the wallet; the public devnet RPC faucet closed, see below.)

## Decisions (spike, 3 Nov)

- **Uploading IDL is deferred** (Slava, 3 Nov). The build server builds
  Anchor 1.x, which dropped the legacy IDL instructions; an on-chain IDL now
  goes through the Program Metadata Program, and client-v2 has none of that
  code. Nothing in the tutorial reads the on-chain IDL. The stages are
  Writing buffer, Deploying, Confirming, with Building and Funding your
  wallet before them when they apply: three to five. Follow-up queued with
  Lead. `tutorial-runs` is updated through `/opsx:update` in this PR.
- **The devnet RPC faucet is closed** (found 3 Nov, after the spike):
  `requestAirdrop` on `api.devnet.solana.com` answers 410 "Request test SOL
  at https://faucet.solana.com". The funding stage still asks first, and a
  refusal ends the run `no_funds`; the faucet card (Open faucet, the address
  to copy, Try again) is the main path for now (Slava, 3 Nov). A faucet of
  our own is a separate ticket.
- **Funding works signed out** (Slava, 3 Nov). The editor's `airdrop`
  command requires GitHub sign-in (`checkSignedIn`); that gate is the
  browser's own, since the request goes to the public devnet RPC, which
  limits per IP. The tutorial promises a wallet with free test SOL, so its
  funding calls the RPC's airdrop directly. The editor keeps its gate.
- **The keypair is already kept.** `build` mints the program keypair when
  the workspace has none and writes `declare_id!` with it
  (`commands/build/build.ts`); it lives in `.workspace/program-info.json`,
  which sync carries and never drops (`keepLocalKeypair`). A later deploy of
  the same workspace is therefore an upgrade with no extra work.
- **The editor's deploy is not reused as a command.** It asks in the
  terminal (airdrop confirm, failed-build confirm, cancel) and reports no
  stages. The tutorial deploy reuses its parts instead:
  `BpfLoaderUpgradeable`, `additionalProgramLen`, `airdropTopUp`, and
  `sendAndConfirmTxWithRetries`, which `deploy.ts` exports unchanged. No
  editor behaviour changes.
- **Recognition after a reload** reads the program's ProgramData account:
  bytes 4..12 are the slot of its last deploy or upgrade, which an extend,
  a buffer write or a call never moves. That slot's block time at or after
  the interrupted run's start (within a minute of device clock skew) means
  that run landed; its signature is the program's signature in that slot.
  Review (3 Nov) found the newest-signature shortcut taking an interrupted
  upgrade's extend for the upgrade.
- **The wallet's right to deploy** is checked before any SOL is locked: an
  upgrade authority that is another wallet, an immutable program, or a
  first deploy without the program keypair stop with a failed card, where
  the editor's deploy checks the same in `checkProgram`.

## Split

- **This PR (model):** the deploy runner, funding, recognition, the act
  runner that composes the acts, `tutorial_action_run` for deploys, the
  spec update. Unit tests with a stubbed connection.
- **Next PR (cards, after the feed shell, HOO-2351 in #227, lands):** the

## Tasks

- [x] **1. Run facts.** `RunResult`'s failed deploy gains a `no_funds`
  variant with `balance` and `cost` in lamports and the wallet `address`,
  the facts of Almaz's line and the address row; the landed deploy's
  `lamports` is null when recognised after a reload.
- [x] **2. Explorer URLs.** `devnetExplorerUrl({ kind, value })` in
  `shared/lib`, always `?cluster=devnet`.
- [x] **3. Funding.** `fundForDeploy({ chain, address, need, capSol,
  onShort })`: nothing when the balance covers `need`; else one airdrop of
  `airdropTopUp(shortfall, capSol)`, then the balance decides, read up to
  three times a slot apart, confirmed or not. A refusal, a rate limit or a
  balance that never moved answers `{ ok: false, balance, message }`, which
  `runDeploy` turns into `no_funds` with the cost.
- [x] **4. Deploy runner.** `runDeploy(port, act, onStage)` over a
  `DeployPort`; `realDeployPort` wraps the editor's loader calls, devnet
  only. No wallet -> `no_wallet`; Funding first when short; Building when
  stale or a build-and-deploy; the authority and keypair check; Writing
  buffer, Deploying, Confirming; cost = balance before the buffer minus
  after; a throw is a failed result, reported with its stage.
- [x] **5. Act runner.** `actRunner(runs, recognise)` dispatches by act;
  an act with no runner answers `failedResult`. `tutorialRunner` wires the
  deploy and build-and-deploy acts for the frame's `PgConversation.init`.
- [x] **6. Recognition.** `recogniseDeploy(input)` returns the landed
  result or null; after a load the store asks `Runner.recognise` once per
  run the save held in flight and dispatches `recognised`, which the
  reducer folds through `ended`.
- [x] **7. Telemetry.** `tutorial_action_run` on the tutorial tracker,
  emitted by the reducer when any act ends and, through the `interrupted`
  action, once per run a reload interrupted. Unexpected throws go through
  the logger with `report: true`; expected stops log a warning with the
  reason, never a key.
- [x] **8. Spec.** `/opsx:update`: stages without Uploading IDL, "n of m"
  three to five, signed-out funding, recognition by the deploy slot.
- [ ] **9. By hand on devnet:** a first deploy from an empty wallet, an
  upgrade keeping the id, a refused airdrop reaching `no_funds`. Moves to
  the cards PR: until a frame passes `tutorialRunner` to
  `PgConversation.init`, no act card can run it.

need engine work this PR does not have (the deployed content recorded per

- [x] **10. Wire the runner.** `tutorialRunner` into `PgConversation.init`

### Design gaps (decided here, checked by Design alignment 3 Nov)

- No-wallet card: "No wallet" / "A deploy pays from a Playground wallet.
  Create one in this browser and the deploy runs." with primary "Create
  wallet"; no connect option (the tutorial always deploys from the
  Playground wallet). The prototype draws no no-wallet state.
- The prototype's code drops the IDL line the `tutorial-runs` spec gives
  the landed card; the code wins, and the spec is corrected when the change
  is updated.
- The terminal bar reads "Deploying" without the stage until the bar
  learns the conversation's stages (the bar's own follow-up).
- The prototype's Log unfolds the deploy's log in the card; the result
  holds no log, so Log opens the terminal, where the deploy printed.
