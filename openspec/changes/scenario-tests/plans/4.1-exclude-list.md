# 4.1 Exclude list and the quality tools: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `yarn spec:coverage` fails on every scenario of `openspec/specs/` that has no test titled
`<capability>: <scenario>`, except the scenarios a committed exclude list names, and the list only shrinks. A
`quality-spec-tests` skill writes the missing tests and shrinks the list.

**Architecture:** The quality tools share the `quality-` prefix, keep their code in their own skill folder under
`.claude/skills/`, and are listed together by `make help` through a root `Makefile.quality`. The coverage gate moves
to `.claude/skills/quality-spec-coverage/`; CI and `yarn run check` reach it through `yarn spec:coverage`. Developer
flows (regenerating the list, linting the gates) exist only as Make targets.

**Tech stack:** Node ESM (`.mjs`), `node:test`, GNU Make, Claude Code skills. No new dependency.

**Spec:** [`../specs/scenario-tests/spec.md`](../specs/scenario-tests/spec.md), as Task 1 revises it.

## Global constraints

- Specs are read from `openspec/specs/` and the active changes, never `openspec/changes/archive/`.
- The key is `<capability>: <scenario>`, matched exactly against a literal, double-quoted title.
- Only scenarios under `openspec/specs/` are gated. A scenario only an active change names is reported, not gated.
- A `(manual)` scenario is never owed a test and never belongs in `excluded.txt`.
- Scripts run through `node`, `yarn`, or `make`. No shebang, no executable bit.
- `package.json` keeps only `spec:coverage` (the gate). Developer-only flows are Make targets, never yarn scripts.
- The checker reads no clause text in this plan: clause and verb rules are task 2.2 and decision 12.
- No Python. Comments are one line, the non-obvious why. British English in new prose, no em dashes.
- Markdown is formatted by markdownlint (`yarn check-md`), never Prettier.
- `client-v2`'s `check-format` and `lint` do not cover `.claude/skills/`; run
  `yarn --cwd client-v2 prettier --check ../.claude/skills/quality-spec-coverage` by hand.
- Two commits, one conventional-commit line each, no body, no co-author trailer, no push:
  1. `feat(quality): gate scenario coverage on a shrink-only exclude list` (Tasks 1 to 6)
  2. `feat(quality): add quality-spec-tests to cover listed scenarios` (Task 7)

## Review focus

1. The base branch has no `excluded.txt` (this PR introduces it): the base comparison is skipped, not run against an
   empty list, or every line fails.
2. A fixture in `spec-coverage.test.mjs` titled with a real capability and scenario covers that scenario in the real
   run. Fixtures use the capability name `fixture-capability`, which has no `spec.md`.
3. A `test.skip`, `test.fixme`, `it.skip`, `it.todo`, `describe.skip`, or `test.describe.skip` titled with a key
   does not cover the scenario.
4. A blank line, a `#` comment, or trailing spaces in `excluded.txt` are ignored; a duplicate line fails.
5. A line naming a `(manual)` scenario fails as stale, so the list never hides a manual mark.

### Task 7: The `quality-spec-tests` skill, commit 2

**Files:**

- Create: `.claude/skills/quality-spec-tests/SKILL.md`; add a `quality-spec-tests` target to `Makefile.quality`
  only if the skill needs a script, otherwise none (a skill is started from Claude Code, not from Make).

**Contract of the skill** (`argument-hint: "<capability> | <capability>: <scenario> [--opus]"`):

1. Resolve the targets: every line of `excluded.txt` for a capability, or the one named key; a key not in the list
   stops with "not on the exclude list".
2. For each scenario, start one subagent with the Agent tool: model `sonnet`, effort `xhigh`; with `--opus`, model
   `opus`, effort `xhigh`. The user set both values; the skill states them, so they are not the agent's own choice.
3. The subagent's brief:
   - read the scenario's clauses from `openspec/specs/<capability>/spec.md`;
   - read product code only to learn how to drive it (selectors, routes, function names); assertions come from the
     THEN clauses, never from what the code does;
   - pick the level by decision 4 of the `scenario-tests` design (integration or end-to-end) and follow
     `client-v2/AGENTS.md` for where a test goes;
   - title the outer `describe`, or the Playwright `test`, with the key; GIVEN and WHEN as nested titles or hooks,
     THEN as the `it` or `test.step`;
   - never edit product code, specs, or other tests.
4. Remove the key's line from `excluded.txt`, run the one test file, and run `yarn --cwd client-v2 spec:coverage`.
5. Report per scenario: the test file, pass or fail with the failing output, the line removed. A failing test stays
   red and is handed to the developer, who decides the fix. The skill commits nothing.
