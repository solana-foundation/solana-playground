# 2.2 Connections in `entities/cluster`

## Why

The current connection is read through one facade, `PgConnection`, but building a connection and tracking its state
are spread out:

| Concern | Where |
| --- | --- |
| Building a `Connection` | `utils/connection.ts` (`PgConnection.create`, the read-buffer connection, the genesis-hash probe), `commands/deploy/bpf-loader-upgradeable.ts`, `commands/sugar/utils/metaplex.ts`, `utils/js-runtime/js-runtime.ts` (the user's `pg.connection`), `utils/playnet/rpc.ts` |
| Cluster detection | `getKnownCluster` and the genesis-hash switch in `utils/connection.ts` |
| Health and status | `effects/connection/`, `hooks/useConnection.tsx`, `providers/solana/SolanaProvider.tsx`, `widgets/session-footer/model/use-cluster-status.ts`, `widgets/status/model/` |

Each builder chooses its own commitment and options, and each status reader polls or subscribes on its own.

Explorer keeps this in `entities/cluster` (`/Users/rogaldh/Projects/solana-explorer/app/entities/cluster`): `api/get-rpc.ts`
hands out one cached client per URL, `model/cluster-provider.tsx` holds the selected cluster and its status, and the
hooks (`use-solana-rpc`, `use-cluster-info`) are how every caller reads them.

## Target

In the slice 2.1 creates:

- `api/`: the only module that constructs a web3.js `Connection`: one cached instance per endpoint and commitment,
  bounded like Explorer's `MAX_CACHED_RPCS`, plus the read-buffer connection and the genesis-hash probe built from it.
  Every builder in the table above calls it instead of `new Connection` or `PgConnection.create`.
- `model/`: the selected connection, its cluster and its health, as one store with change events; `PgConnection`
  becomes a thin facade over it (or its callers move to the slice's API where that is a path change only), so the
  roughly 55 files that read `PgConnection` keep working unchanged in this task.
- One hook for React callers that reads the connection and its status; the status widgets and the session footer
  read it instead of polling on their own.

Stays where it is: the connection code generated into exported projects (`features/project-export`,
`frameworks/native/export.ts`), which is the user's code, not the app's.

## Must not change

- Behaviour visible to the user, ids, `aria-label`s, test ids, and telemetry events.
- The web3.js `Connection` type every caller receives; moving to `@solana/kit` is out of scope.
- The stored formats 2.1 keeps.

## Out of scope

- `@solana/kit`.
- Moving the roughly 55 readers of `PgConnection` onto the slice's API beyond what the facade needs.
