# Refused-call goals, argument values and record lines: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans
> (inline). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `tutorial.json` can express Lumberjack step 3 and Zero Copy steps
2–3, the check accepts them, and the engine passes a `refused` step only on
the refusal the result shows.

**Architecture:** Schema and types first (`entities/tutorial`), then the
engine (`features/tutorial-conversation/model`): the failed call result
gains `refused`, `judgeGoal` gains a `refused` case, the reducer gains a
refused branch and argument values on `act`. AUTHORING.md last.

**Tech Stack:** TypeScript, JSON Schema (ajv, as `checkDefinition` uses),
vitest in-source blocks.

**Spec:** `openspec/changes/archive/2026-11-02-tutorial-refused-call-goals/`
(proposal, design, both spec deltas). As shipped, the schema uses `anyOf`
over `required` rather than `minProperties`, and `RefusedError` is a union.

## Global Constraints

- In-source test blocks per `client-v2/AGENTS.md`; no spread to build test
  fixtures (explicit copies).
- No nested ternaries; no empty `catch`; comments name symbols, never lines.
- Error codes are whole numbers; Anchor's custom errors start at 6000.
- Commits: Conventional Commits, `(client-v2)` or `(tutorials)` scope,
  `(HOO-2502)` suffix, no attribution lines.

## Review Focus

1. A failed result with no `refused` (no wallet, send failed) on a `refused`
   step: must not pass. Test in `goals.ts`.
2. A `refused` goal giving both error and log: both must match. Test in
   `goals.ts`.
3. A refusal on a step whose goal is `call` (Lumberjack step 4, chop before
   the refill): stays `failed`, Explain still offered. Test in `reducer.ts`.
4. Saved progress holding a `refused` run reloads as refused; unknown
   status still drops. Test in `progress.ts`.
5. A learner value for a fixed-value argument is ignored (the definition
   wins). Test in `reducer.ts`.

**Interfaces (Produces):**
```ts
export type CallArg =
  | string
  | { name: string; value: string | number }
  | { name: string; value: number; add: number };
// ActBeat call: { instruction: string; args?: CallArg[] }; ActBase gains record?: string
export type Goal =
  | ...existing
  | {
      kind: "refused";
      instruction: string;
      error?: { name?: string; code?: number };
      log?: string;
    };
export const argName: (arg: CallArg) => string; // exported from entities/tutorial
```

Schema: `refused` requires `kind`, `instruction` and `anyOf` `error`/`log`;
`error` is an object with `name` (string, minLength 1) and/or `code`
(integer ≥ 0), `minProperties: 1`. Call args items: `oneOf` string |
`{name, value: string|integer}` | `{name, value: integer, add: integer}`,
`additionalProperties: false`. `record`: string, minLength 1, on any act.

**Interfaces:**
- Consumes: `Goal` `refused`, `CallArg`, `argName` from Task 1.
- Produces:
```ts
export interface Refusal {
  instruction: string;
  /** null for a refusal with no error code: a panic, out of memory */
  error: { code: number; name: string | null } | null;
}
// failed run|call RunResult: + refused?: Refusal
// RunRecord: + { status: "refused"; at; took; result }
```

- [ ] Step 1: failing tests in `goals.ts`:
  - `passes a refusal with the goal's error, by name, code or both`.
  - `fails another error, another instruction, a confirmed call, and a failure that never reached the program`.
  - `matches the log pattern over the whole transaction log, case-blind`
    (Zero Copy: "too big" log fails, "memory allocation failed, out of memory" passes).
  - `needs both the error and the log when the goal gives both`.
  - `a refusal passes no call goal`.
- [ ] Step 2: failing tests in `reducer.ts`:
  - `a refusal the goal expects is recorded refused and passes the step` (event `tutorial_step_passed` via `chat`).
  - `a refusal the goal does not expect stays failed and is explained` (`explain` effect on a step with goal `call`).
  - `sends fixed values and grows a value by each run that landed`: values 20480, then 30720 after an ok run, 30720 again after a refused-but-not-passing failure.
  - `the definition's value wins over a learner's for a fixed argument`.
- [ ] Step 3: failing test in `progress.ts`: `a refused run reloads as refused`.
- [ ] Step 4: run the three files → fail.
- [ ] Step 5: implement. Argument values: in `act`, for a call beat,
  `args = { ...learner values for string args, [name]: String(value + add × okRuns) }`
  where `okRuns` counts `p.runs[beat.id]` with `status === "ok"`.
- [ ] Step 6: the three files and `view.ts`, `engine.test.ts`,
